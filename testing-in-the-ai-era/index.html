Chapter 1 · What tests are forA test is executable product intent

A good test says what the system promises. Then it proves the promise on every run.

When

a staff member reactivates a withdrawn student

Then

the student becomes active, the change is recorded, and no withdrawal notice is sent

Wiring statement

expect(emailService.send).not.toHaveBeenCalled()

Describes one implementation.

Product statement

expect(withdrawalNotices).toEqual([])

Describes what an observer sees.

Test the promise, not the route the code currently takes.

Chapter 2 · The AI-era inversionEverything that unit test did not prove

Every red break below can ship while the mock-heavy unit test stays green.

  1. Unproven Auth + input The request may never reach the handler.
  2. Unproven Route wiring The request may call the wrong code.
  3. Unproven Real account read The query may use the wrong key.
  4. Unproven Database write The update may match zero records.
  5. Unproven Downstream work The background job may do nothing.
  6. Unproven Final state Access and notifications may stay wrong.

A second common shape

Mock a query → mock a publisher → assert both mocks were called. The test knows the route, but never checks the destination.

Chapter 2 · The AI-era inversionAI amplifies false confidence

Agents are excellent at copying visible structure. A mock-heavy test exposes the structure and the expected answer together.

Closed implementation loop

  1. Read the current code.
  2. Mock every collaborator.
  3. Assert the same calls.
  4. Report high coverage.

Fast green. Weak evidence.

Independent product loop

  1. Read the requirement.
  2. Seed the real preconditions.
  3. Act through the public boundary.
  4. Assert the visible result.

Useful green. Refactor freedom.

Chapter 2 · The AI-era inversionUnit tests still have a job

“Last resort” does not mean “never.” It means every lower-level test needs a concrete reason.

ƒ

Pure logic

A formula, parser, state machine, or date calculation with no collaborators.

×N

Large input matrix

Hundreds of combinations where broad setup adds cost but no confidence.

!

Unreachable failure

A precise error path that cannot be triggered honestly through a public boundary.

∅

Async absence

A negative side-effect rule with no observable completion signal.

Choose the lowest level that adds evidence—not the lowest level that is easy to mock.

Chapter 3 · Humans and agentsTDD becomes an agent contract

The test is the small, executable agreement between product intent and generated code.

  1. Specify Write the observable behavior.
  2. Fail Prove the test can detect its absence.
  3. Generate Let the agent implement one increment.
  4. Verify Run the real path and inspect the diff.
  5. Keep The contract becomes regression coverage.

The agent can change the implementation. It should not negotiate with the expected product outcome.

Chapter 4 · Making broad tests readableThree honest ways to prove a negative async effect

There is no universal trick. Pick the strongest completion boundary the system honestly gives you.

01

Wait for a causal signal

await driver.waitForStatus();
const emails = driver.emails();
expect(emails).toEqual([]);

The signal must happen after the email decision. Strong broad coverage, but it depends on critical ordering details and is hard to write as black-box TDD.

02

Expose workflow completion

await driver.waitForDone(runId);
const emails = driver.emails();
expect(emails).toEqual([]);

Use a durable outbox, task state, or completion seam. Best when completion is itself useful to product or operations.

03

Use a focused unit test

const commands = policy.for(reversal);
expect(commands).not.toContainEmail();

Isolate the branching policy when no honest completion signal exists. Keep one positive integration test proving the email pipeline works.

Chapter 4 · Making broad tests readableDrivers turn wiring into a story

The spec says what exists, what happens, and what becomes visible. The driver knows how.

Without a driver

await students.insertOne(student);
await courses.insertOne(course);
await enrollments.insertOne(enrollment);
await lessons.insertMany(lessons);
const response = await http
  .get(progressPath(studentId))
  .expect(200);
→

With given / when / then

const progress = await driver.given
  .student((student) =>
    student.withId(studentId))
  .given.course((course) =>
    course.withId(courseId).withLessons(4))
  .given.enrollment((enrollment) =>
    enrollment.withStudent(studentId))
  .when.getProgress(studentId);

The spec owns meaning. The driver owns mechanics.

Chapter 4 · Making broad tests readableHow to write a good test driver

A driver is a thin domain language over real setup, a real action, and real outcomes.

The shape

driver.given
  .student((student) => ...)
  .given.course((course) => ...)
  .when.getProgress(studentId);

const saved = await driver.then
  .storedProgress(studentId);

The rules

  • given records setup and returns the driver
  • when writes pending data, then performs one real action
  • then reads outcomes from the real system
  • the spec creates and connects important IDs
  • all expectations stay in the spec

Do not hide the test inside the driver

One driver belongs to one feature spec. No async given, no entity returned from setup, no expected-value helpers, and no mocked internal services.

Chapter 4 · Making broad tests readableBuilders make valid data. Seeders hide fixed worlds.

Two layers remove noise without hiding the condition under test.

  .given.progress((progress) =>

Hides repeated invariants. The test body shows only what changes.

Visible in the test load-bearing variation Hidden in the seeder fixed invariant

Chapter 4 · Making broad tests readableHow to write a good builder

A builder owns one valid entity. Tests state only the fields that matter.

One predictable shape

new StudentBuilder()
  .withId(studentId)
  .withProgram('software-engineering')
  .withEnrollment((enrollment) =>
    enrollment
      .withCourse(courseId)
      .withStatus('active'))
  .build();

The rules

  • start with valid, boring defaults
  • use withField(value) for scalar fields
  • use a builder callback for every nested entity
  • add setters only when a test varies that field
  • add convenience methods only after a repeated real use

Never replace a builder with an options object or a hand-written database record.

Chapter 5 · Making broad tests fastThe operating rules

Optimize for confidence per test—not tests per class.

  1. Start at the real product entry point.HTTP API, command-line input, or client app.
  2. Keep internal collaborators real.Seed the state their real handlers read.
  3. Fake only true external delivery.Capture the email, task, analytics event, or file.
  4. Assert exact observable outcomes.State, events, return values, and side effects.
  5. Make async completion deterministic.Never confuse a timeout with proof.
  6. Use unit tests with a concrete reason.Pure logic, large matrices, unreachable paths, or honest negative checks.

Seed the real world. Run the real path. Give humans and agents a green worth trusting.
