One App to Test Them All

The Ai-Tutor backend test refactor — what tests are, why ours hurt, the shared harness that fixes it, and your part in the migration.

Fellowship onboarding · presented by Or · July 2026

Chapter 1 · What are testsA robot that re-checks your work

A smoke detector doesn't stop fires. It tells you the moment one starts — before the house burns down.

A test is a small program that runs part of our app and checks the result. When someone breaks something, a test turns red before users notice. We have hundreds; they all run automatically on every change. Why bother:

  • Change without fear. Rewrite code and know in minutes whether you broke a promise the old code kept.
  • Executable documentation. A test says "when X happens, the system does Y" — and proves it on every run. Docs go stale; tests can't.
  • Catch regressions. A regression is an old feature that a new change silently broke. Tests catch it before users do.

Anatomy of one test: setup → act → assert

Build the world, do the one thing, check the outcome. Real code from our repo:

it('derives withdrawn status for a registration with a Z grade letter', async () => {
  // setup: put one registration in the database
  await seedRegistration(studentId, {
    termNumber: 2,
    grade: { letter: 'Z', numerical: null, updatedAt: new Date() },
  });

  // act: call the endpoint like a real admin would
  const { body } = await driver.request().get(path())
    .set('Authorization', driver.auth(viewAdmin)).expect(200);

  // assert: check the answer
  expect(body.registrations[0].status).toBe('withdrawn');
});

Chapter 2 · Two kinds of testsThe bench and the test drive

Unit test: take one engine part out of the car and spin it on the bench. Integration test: put the parts together and drive around the block.

Unit — the part on the bench

One piece of logic in isolation: a grade formula, a date calculator. Milliseconds fast, no database, no network.

But it can't tell you the car drives. The part may be perfect and the car still won't start.

Integration — the test drive

The real pieces wired together: real endpoint, real logic, real database. Slower, but it fails the way production would fail.

One integration test can cover what ten unit tests only hint at.

Our philosophy

Write every test at the highest realistic level — the default is integration. A mock (a stand-in fake object) is the last resort, allowed only for external services that truly cannot run in a test.

A stub that drifts from real behavior makes a green test lie.

This rule lives in the repo's /write-tests skill. It is the single most important idea in this deck.

Chapter 3 · The NestJS + Jest problemEvery file opens its own restaurant

Booting our NestJS backend is like opening a restaurant: hire staff, stock the kitchen, unlock the doors. Our old specs did that per file — to serve one table.

What each spec file pays

  • Boots its own NestJS app (a TestingModule).
  • And clones a fresh migrated MongoDB database.

Why Jest makes it worse

  • Jest — our test runner — runs each file in a separate worker process. Workers share nothing.
  • So the boot cost is paid again for every file.

Hundreds of files, one app boot and one DB clone each — a slow suite. Slow tests get skipped, and skipped tests catch nothing.

Chapter 3 · The NestJS + Jest problemThe coping trick: stubs

To keep each per-file app small and quick to boot, people replaced real logic with stubs — hand-written stand-ins.

Real code from the old admin spec:

@QueryHandler(GetUserQuery)
class FakeGetUserQueryHandler implements IQueryHandler<GetUserQuery> {
  constructor(private readonly dbService: DBService) {}

  execute(query: GetUserQuery) {
    return this.dbService
      .collection<UserDao>('users')
      .findOne({ _id: new ObjectId(query.userId) });
  }
}

Looks harmless. It is a hand-copied guess at what the real handler does. Then the real handler changes — and the stub doesn't. The test keeps checking the stub and stays green while the real path is broken. A handler refactor can break production while the stubbed test passes for the wrong reason.

Slow and less reliable — the two problems named in the driver README. Both share one root: every file builds its own private world.

Chapter 4 · Our integration-test visionBoot once, use everywhere

One shared, real Nest app boots once per test run — in Jest's globalSetup — and listens on a local port. Specs don't boot anything. They seed data and make HTTP calls. The restaurant opens once in the morning; every test is just another customer.

  1. Spec Test file Seeds its own rows, then calls the app.
  2. Real HTTP A genuine network request to the shared port.
  3. Real JWT guard The test signs a real token with the app's secret. No guard overrides.
  4. Real Controller The production route, validation included.
  5. Real CQRS handler No stubs. The code production runs.
  6. Real MongoDB Real reads, real writes, real indexes.

When the real path throws, the usual cause is missing seeded state — so seed the state, don't fake the step.

Chapter 4 · Our integration-test visionSeams, and cleanup without teardown

Two ideas make one shared app workable: fake only at the seams, and clean only what you created.

The seam — the shirt analogy

A seam is the exact line where one piece of fabric is stitched to another. Our code has seams too: where it stitches onto an external service — Segment analytics, RabbitMQ.

Those can't run in a test. We cut the stitch exactly there and sew in a fake that captures what would have been sent. Everything inside the shirt stays real.

Isolation — the shared kitchen

The shared DB is never wiped — wiping would destroy other tests' data mid-run. Instead, every spec seeds fresh unique ids (ObjectIds), reads only its own, and cleans up exactly what it created.

No one bleaches the whole kitchen; everyone washes their own pots.

Chapter 5 · The core piecesThe harness: test/api/driver/

Seven small files. You will touch the first two daily; the rest work for you in the background.

  • api.driver.ts — ApiDriver, the stable core: HTTP, auth, DB, seeding.
  • use.api.driver.ts — useApiDriver(), wires the driver into the test lifecycle.
  • test.scope.ts — TestScope, the cleanup ledger.
  • scoped.collection.ts — inserts that clean themselves up.
  • claimed.namespaces.ts — who owns shared values (cohorts).
  • interfaces.ts — the contracts; the one door in for seam types.
  • seams/ · test-hooks/ · clients/ — one folder per faked boundary.

ApiDriver — your remote control

class ApiDriver {
  request()                  // supertest against the shared app
  auth(user)                 // mint a REAL signed JWT for this user
  db                         // the shared Mongo connection
  collection<T>(name)        // auto-owning collection wrapper
  seedUser(configure?)       // insert a user via the UserBuilder
  seedAdmin()                // a user with admin permissions
  seedCalendar(dao)          // cohort calendar, via the claim registry
  uniqueEmail() / uniqueKey(prefix)  // collision-free values
}

Small on purpose. Domain helpers compose around it — they don't pile onto it.

Chapter 5 · The core piecesWiring you can't get wrong

useApiDriver() hooks the driver into Jest's lifecycle so cleanup always happens. This is the whole file: 

export function useApiDriver(): ApiDriver {
  const driver = new ApiDriver();

  beforeAll(() => driver.connect());
  beforeEach(() => driver.scope.checkpoint());
  afterEach(() => driver.cleanupSinceCheckpoint());
  afterAll(async () => {
    await driver.cleanupScope();
    await driver.close();
  });

  return driver;
}

TestScope — the receipt ledger

Every seed writes a delete-receipt; cleanup cashes in the receipts — yours only. 

scope.ownId('users', id)                    // receipt: delete this _id
scope.ownBy('email_records', { userId })    // receipt: delete by filter
scope.ownCustom(label, run)                 // receipt: run this cleanup step
scope.checkpoint()                          // draw a line in the ledger

The checkpoint separates file fixtures from per-test data: receipts written before it (in beforeAll) survive the whole file; receipts written after it are cleaned after each test.

Rule: call useApiDriver() as the first statement in the describe. Jest runs hooks in order — the driver's checkpoint must register before any of your own beforeEach seeding.

Chapter 5 · The core piecesSeeding that can't leak or collide

Two guards keep hundreds of specs safe on one database.

ScopedCollection — inserts that own themselves

The default seeding path. Every insert registers its own receipt:

async insertOne(doc): Promise<InsertOneResult<T>> {
  const result = await this.inner.insertOne(doc);
  this.scope.ownId(this.inner.collectionName, result.insertedId);
  return result;
}

raw() is the escape hatch for Mongo APIs it doesn't wrap — a raw insert must be paired with a manual scope.own* receipt.

The claim registry — bounded values

Fresh ids can't collide, but some values come from a small fixed set — like cohorts. Two specs will eventually pick the same one and flake only when run together. The registry names an owner per value, and seedCalendar checks it before inserting: 

export const COHORT_CALENDAR_OWNERS = {
  [CohortTermDescriptor.SEPTEMBER_2025]:
    'course.registration.admin.controller.spec.ts',
  ...
};
// inside driver.seedCalendar():
assertClaim(COHORT_CALENDAR_OWNERS, dao.cohort, 'cohort calendar');

A second claimer fails at seed time, with the owner's name — not weeks later as a mystery flake. And absence is a claim too: "this cohort has no calendar" must also be registered.

Chapter 5 · The core piecesFaked boundaries, and the spec to copy

One folder trio per faked boundary. Today: analytics (Segment) and the task transport (RabbitMQ).

  • seams/ — the swap: replace the network client with a recorder.
  • test-hooks/ — test-only HTTP routes to read the captures back.
  • clients/ — the spec-side wrapper: driver.analytics.waitForEvent(...).

The canonical spec — copy this shape

test/admin/course.registration.admin.controller.spec.ts:

describe('Course registration admin', () => {
  const driver = useApiDriver();          // first statement — always

  beforeAll(async () => {                 // file fixture: claimed cohort
    await driver.seedCalendar(buildCalendarDao(STATUS_COHORT, [...]));
  });

  beforeEach(async () => {                // per-test: fresh admin
    viewAdmin = await driver.seedUser((user) =>
      user.withPermissions([{ title: 'course-registration-view' }]));
  });

  it('rejects a caller without the view permission', async () => {
    await driver.request().get(path())
      .set('Authorization', driver.auth(noPermsUser)).expect(403);
  });
});

Real JWT auth, claimed calendar seeding, per-test admins, assertions on the HTTP response, the DB, and captured analytics. Every new spec starts from this file.

Chapter 6 · Your taskHow the work flows

All conversion work runs through the code factory. You don't write the conversion by hand — you own its quality.

  1. An agent converts the spec to the shared driver.
  2. You read the engineering plan, review what the agent did, let it rebase if needed, and approve.
  3. Or merges.

Ground rules

One spec (or one slice) per PR, converted in place — the file doesn't move. A new seam lands in the same PR as its first consumer, never speculatively.

The work splits into two parallel tracks — one fellow each. Both start with warm-ups and end with a capstone that leaves a new harness piece behind for everyone after you.
